# 에이전트와 팀

에이전트는 이름, 맡은 일, 지시, 모델, 도구 범위를 가진 역할이다. 팀은 에이전트 둘 이상을 묶어 역할별로 나눠 일하게 한다.
이 문서는 에이전트와 팀을 만들고, 일을 보내고, 구성원을 멈추고, 자동화를 거는 방법을 설명한다.
버튼과 화면 배치는 [화면 가이드](screen-guide.md)에 자세히 있다.

## 어디서 다루나

| 하는 일 | 위치 |
|---|---|
| 역할 만들기·편집·삭제 | 에이전트 탭 › **역할** |
| 팀 만들기·편집·내보내기·가져오기 | 에이전트 탭 › **팀** |
| 대화를 지켜보는 조언자 | 에이전트 탭 › **조언자** |
| 이벤트 규칙과 프로젝트 훅 | 에이전트 탭 › **자동화** |
| 에이전트·팀과 대화 | 채팅 위의 대화 상대 탭 |
| 진행 상황 보기, 구성원 하나 멈추기 | 채팅의 작업 카드 |
| 화면 입력 제어 켜기 | 채팅 입력창의 화면 입력 제어 버튼(Live 오른쪽) |

## 에이전트(역할) 만들기

### 만드는 순서

1. 에이전트 탭 › 역할에서 **+ 새 역할**을 누른다.
2. 필요하면 템플릿에서 시작한다. 템플릿은 설계자, 구현자, 리뷰어, 테스터, 문서 작성자, 탐색자가 있다.
3. 저장 범위를 고른다. 아래 [저장 범위](#저장-범위)를 본다.
4. 표시 이름, 식별자 이름, 맡은 일, 설명, 지시 사항을 적는다.
5. 모델, 추론 단계, 도구 범위를 고른다.
6. 필요하면 **지식**에서 이 역할에 늘 붙일 지식을 고른다.
7. **저장**을 누른다.

파일은 **저장**을 누를 때만 쓰인다. 삭제는 화면에서 한 번 더 확인한 뒤 한다.
다른 곳에서 그사이 파일이 바뀌었으면 저장을 거부한다. 이때는 다시 읽은 뒤 저장한다.

### 항목과 제한

| 항목 | 뜻 | 제한 |
|---|---|---|
| 식별자 이름 | 역할을 가리키는 이름 | 영문 소문자·숫자·`-`, 2~40자. `main`, `sub`는 쓸 수 없다 |
| 표시 이름 | 화면에 보이는 이름. 비우면 식별자 이름이 보인다 | 40자 |
| 맡은 일 | 한 줄 요약 | 80자 |
| 설명 | 모델이 언제 이 에이전트를 쓸지 판단하는 글 | 1,000자 |
| 지시 사항 | 일하는 방식, 지킬 것, 보고 형식 | 24,000자 |

역할 파일 하나는 64 KiB까지다. 역할 개수에는 제한이 없다.
엔진 내장 역할의 이름은 그 역할을 편집해서 만든 파일에서만 쓸 수 있다.

### 모델과 추론 단계

| 모델 선택 | 뜻 |
|---|---|
| 채팅 모델과 같게 | 채팅에서 고른 모델로 실행한다 |
| 빠른 모델 | 빠른 모델 역할(`@smol`)로 실행한다 |
| 특정 모델 | 계정의 모델 목록에서 검색해 고른다 |

추론 단계는 자동, 낮음, 보통, 높음, 최대 중에서 고른다.

### 도구 범위

| 도구 범위 | 쓸 수 있는 도구 |
|---|---|
| 모든 도구 | 제한 없음 |
| 읽기 도구 | `read`, `find`, `grep`, `glob`, `lsp`, `yield`와 VS 도구 중 읽기 전용 도구 |
| 직접 지정 도구 | 파일에 도구를 직접 적은 역할. 도구 목록은 VS에서 파일을 열어 고친다 |

읽기 도구만 가진 에이전트는 파일을 바꾸지 않는다.

### 저장 범위

| 범위 | 파일 위치 | 쓰임 |
|---|---|---|
| 이 프로젝트 | `<작업 영역>/.pomp/agents/<name>.md` | 저장소에 넣어 팀원과 공유할 수 있다 |
| 내 모든 프로젝트 | `~/.omp/agent/agents/<name>.md` | 이 PC의 모든 프로젝트에서 쓴다 |

같은 이름의 역할이 여러 곳에 있으면 아래 순서에서 앞의 것이 쓰인다. 쓰이지 않는 역할에는 **가려짐** 배지가 붙는다.

1. 내 모든 프로젝트 `~/.omp/agent/agents/`
2. 이 프로젝트 `<작업 영역>/.pomp/agents/`
3. 확장 패키지의 `agents/`
4. 엔진 내장 역할

`.claude/agents`와 `.agents/` 폴더는 읽지 않는다.
이전에 `<작업 영역>/.omp/agents`에 둔 역할은 처음 쓸 때 `.pomp/agents`로 옮긴다. 같은 이름이 이미 있으면 옮기지 않는다.

역할 파일은 에이전트를 실행할 때마다 다시 읽는다. 파일을 고치면 다음 실행부터 반영된다.
`.pomp/agents/*.md`의 프로젝트 역할은 `/recipe`로도 불러올 수 있다.

### 엔진 내장 역할과 POMP 자신

엔진 내장 역할은 task, sonic, scout, reviewer, security-reviewer다. 목록에서 **편집**과 **복제**를 할 수 있다.

- **편집**을 누르면 엔진이 정의한 지시문, 도구, 모델이 채워진 편집 창이 열린다.
- 저장하면 같은 이름의 역할 파일이 생긴다. 엔진은 내장 역할 대신 그 파일을 쓴다.
- 편집 창이 다루지 않는 설정은 엔진 정의를 그대로 옮겨 적는다. 출력 형식과 `spawns`가 그런 예다.
- 그 파일을 삭제하면 내장 역할로 돌아간다.

역할 목록 맨 위의 **POMP**는 채팅에서 사용자와 직접 일하는 에이전트다.
POMP는 그림과 지시(`APPEND_SYSTEM.md`)만 편집할 수 있고 삭제할 수 없다.

### 역할 파일을 직접 고칠 때

역할 파일은 omp 표준 형식이다. 앞머리(YAML) 아래에 지시 본문을 적는다.

```markdown
---
name: "reviewer-strict"
description: "변경된 코드의 버그·예외 처리·보안 문제를 근거와 함께 찾는다. 코드는 바꾸지 않는다."
pomp-title: "꼼꼼한 리뷰어"
pomp-job: "변경 코드 리뷰"
model: "<공급자>/<모델 id>"
thinking-level: "high"
tools: ["read", "find", "grep", "glob", "lsp", "yield"]
---
(지시: 일하는 방식, 지킬 것, 보고 형식)
```

| 키 | 뜻 |
|---|---|
| `name` | 필수. 식별자 이름 |
| `description` | 필수. 모델이 이 에이전트를 언제 쓸지 판단하는 글 |
| `pomp-title` | 화면에 보이는 이름 |
| `pomp-job` | 맡은 일 |
| `model` | `provider/id` 또는 `@smol` 같은 역할. 생략하면 채팅 모델. 목록으로 적으면 앞에서부터 대체 순서다 |
| `thinking-level` | 추론 단계. 생략하면 자동 |
| `tools` | 쓸 도구 목록. 생략하면 모든 도구. 적으면 `yield`가 자동으로 더해진다 |
| `spawns`, `output`, `blocking`, `autoloadSkills` | 엔진이 읽는 키. POMP 편집 창은 다루지 않는다 |

`pomp-`로 시작하는 키는 POMP 화면용이고 에이전트 실행에는 쓰이지 않는다. 엔진은 알 수 없는 키를 무시한다.
POMP가 만들지 않은 파일도 편집하고 삭제할 수 있다. 이때 POMP가 모르는 앞머리 키는 그대로 둔다.

## 팀 만들기

### 만드는 순서

1. 에이전트 탭 › 팀에서 **+ 새 팀**을 누른다.
2. 저장 범위를 고른다. 이 프로젝트 또는 내 모든 프로젝트다.
3. 표시 이름, 팀 식별자, 팀 목표를 적는다.
4. 구성원을 2명 이상 넣는다. 아래 역할 표에서 검색해 `+` 버튼으로 더하고, 위아래로 순서를 바꾼다.
5. 진행 방식을 고른다.
6. 모든 구성원이 따를 지시 사항을 적는다.
7. 필요하면 스위치와 **지식**을 정한다.
8. **저장**을 누른다.

### 진행 방식

| 진행 방식 | 동작 |
|---|---|
| 리더 판단 (기본) | 메인 대화가 일을 나누고 필요한 구성원만 부른다 |
| 동시에 | 모든 구성원에게 한 번에 맡긴다 |
| 순서대로 | 구성원 목록 순서로 진행하고, 앞 구성원의 결과를 다음 구성원에게 넘긴다 |

어느 방식이든 메인 대화가 리더다. 별도 권한이 더 생기지는 않는다.

### 팀 스위치

| 스위치 | 기본 | 동작 |
|---|---|---|
| 구성원 외 에이전트 호출 차단 | 켬 | 팀이 일하는 동안 구성원이 아닌 에이전트를 띄우지 못한다. 읽기 전용 탐색용 `scout`는 허용한다 |
| 격리된 복사본에서 실행 | 끔 | 구성원마다 따로 만든 복사본에서 일한다. [격리된 복사본에서 실행](#격리된-복사본에서-실행)을 본다 |

차단은 그 팀에 보낸 메시지의 응답이 끝날 때까지 유지된다.

### 팀 파일

| 범위 | 파일 위치 |
|---|---|
| 이 프로젝트 | `<작업 영역>/.pomp/teams/<id>.json` |
| 내 모든 프로젝트 | `%APPDATA%\Pomp\teams\<id>.json` |

```json
{ "version": 1, "id": "feature-dev", "title": "기능 개발팀", "goal": "요청한 기능을 설계·구현·검토·테스트까지",
  "members": ["architect", "implementer", "reviewer-strict", "tester"], "mode": "lead",
  "instructions": "공통 지시", "membersOnly": true, "isolation": false }
```

| 키 | 뜻 | 제한 |
|---|---|---|
| `id` | 팀 식별자 | 역할의 식별자 이름과 같은 규칙 |
| `title` | 표시 이름 | 40자 |
| `goal` | 팀 목표 | 400자 |
| `members` | 구성원 역할 이름 목록 | 2명 이상, 상한 없음. 중복 불가. 지금 찾을 수 있는 역할만 |
| `mode` | 진행 방식: `lead` 리더 판단, `parallel` 동시에, `pipeline` 순서대로 | |
| `instructions` | 공통 지시 | 8,000자 |
| `membersOnly` | 구성원 외 에이전트 호출 차단 | 생략하면 켬 |
| `isolation` | 격리된 복사본에서 실행 | 생략하면 끔 |

팀 파일 하나는 32 KiB까지다.

## 일 보내기

### 보내는 방법

| 방법 | 쓰는 법 |
|---|---|
| 대화 상대 탭 | 역할·팀 줄의 **메시지**를 누르면 그 상대의 탭이 열린다. 그 탭에서 보내는 메시지는 그 상대에게 간다 |
| 명령으로 탭 열기 | `/agent 이름` 또는 `/team id`를 메시지 없이 보낸다 |
| 메시지 하나만 보내기 | 입력 막대의 **보낼 대상** 칩에서 상대를 고른다 |
| `@` 목록 | "에이전트·팀" 묶음에서 고른다. 대상만 바뀌고 입력한 `@` 글자는 지워진다 |
| 명령으로 바로 보내기 | `/agent 이름 메시지` 또는 `/team id 메시지` |
| 편집기에서 | 우클릭 POMP ▸ 에이전트·팀에게. [편집기 우클릭 메뉴](screen-guide.md#2-편집기-우클릭-메뉴)를 본다 |

메시지 하나의 대상은 한 번에 하나다. 팀, 에이전트, 이 대화에서 실행한 에이전트 중 하나를 고른다.
대상을 찾지 못하면 보내지 않고 오류를 보인다.

### 팀에 보낼 때

POMP는 보내기 직전에 팀 파일을 다시 읽어 확인한다. 그다음 팀 안내와 사용자 메시지를 함께 메인 대화에 넘긴다.
편집기 컨텍스트, 첨부, 그 팀에 체크한 지식도 함께 간다.

팀 안내에는 아래 내용이 들어간다. 채팅에서는 이 안내가 "팀: 기능 개발팀" 같은 카드로 접혀 보인다.

- 팀 목표, 진행 방식, 구성원의 이름·맡은 일·모델
- 구성원끼리 서로 조율하고, 공유 파일은 편집 전에 조율하라는 규칙
- 빌드·테스트·리뷰처럼 검증을 맡은 구성원에게는 할 확인을 할당에 적으라는 규칙
- 끝나면 구성원별 결과, 바꾼 파일, 남은 문제를 보고하라는 요청

하위 에이전트는 시키지 않은 빌드나 테스트를 하지 않는다. 확인이 필요하면 팀 지시나 메시지에 적는다.

엔진은 하위 에이전트를 동시에 32개까지 띄운다. 하위 에이전트는 다시 하위 에이전트를 띄우지 못한다. 승인 모드와 관계없다.

### 에이전트 하나에게 보낼 때

보내는 방법은 두 가지다.

| 방법 | 대상 | 동작 |
|---|---|---|
| 새 일로 보내기 | 역할 이름. 엔진 내장 역할도 된다 | 메인 대화가 그 에이전트 하나만 새로 실행하고, 사용자 메시지를 그대로 맡긴다. 그동안 다른 에이전트는 띄우지 않는다 |
| 이어 보내기 | 보낼 대상 목록의 "이 대화에서 실행한 에이전트" | 이 대화에서 **실행 중인** 에이전트에게 메시지를 보낸다. 그 에이전트는 자기 맥락을 이어서 답한다 |

완료·실패·중단된 구성원은 직접 전달 대상에서 빠진다. 새 일은 역할 에이전트나 대화 상대 탭에서 보낸다.
기존 실행 중 구성원에게는 메인 에이전트의 중계 없이 엔진 RPC로 직접 보낸다. 채팅의 `전달 수락` 표시는
구성원이 메시지를 받았다는 확인이지 작업 완료가 아니다. 네이티브 Codex 구성원에게는 진행 중 턴의 다음
메시지(`followUp`)로 전달하므로 현재 턴을 즉시 수정하지 않는다.
메시지 전달도 쓰기 도구라서 권한 모드에 따라 확인을 받을 수 있다.

에이전트끼리도 메시지를 주고받는다. 오간 메시지는 채팅과 해당 대화 상대 탭에 보인다.

### 보낼 수 없는 경우

- 프로젝트 정책(`.pomp/permissions.json`)이 검토 전용 모드이면 팀과 에이전트에게 보내기를 거부하고 이유를 보인다.
- 격리 팀은 작업 영역이 Git 저장소가 아니면 보내기 전에 거부한다.
- 메인 대화가 응답 중일 때 새 역할·팀에 보낸 메시지는 [대기열](#응답-중에-보낸-메시지-대기열)에 들어간다. 실행 중인 기존 구성원에게는 직접 전달한다.

## 대화 상대 탭

채팅 위, 대화 이름 아래에 대화 상대 탭이 있다.
맨 앞의 **기본 (POMP)** 탭은 닫을 수 없다. 그 뒤에 연 에이전트·팀 탭이 붙는다.

- 탭 개수에는 제한이 없다. 많으면 탭 줄이 가로로 넘어가고, 탭의 `×` 버튼으로 닫는다.
- 진행 중인 탭을 닫으면 확인을 다시 묻는다. 확인하면 해당 작업·승인과 엔진을 끝내며 현재 탭이었다면 기본 탭으로 이동한다.
- 실행 중 다른 대화 상대 탭을 누르면 즉시 이동한다. 원래 응답은 계속 진행하며 탭별로 동시에 요청할 수 있다.
  비활성 탭의 응답·질문은 그 탭으로 돌아오면 표시된다.
- 활성 탭이 이 대화의 상대다. 메시지를 보낼 때마다 초기화되지 않는다.
- 상대는 대화마다 저장된다. 새 대화는 **현재 탭**의 상대를 유지한다. 대화 목록에도 상대가 보인다.
- 대화 중에 상대를 바꾸면 다음 메시지부터 적용된다.

### 탭마다 보이는 것

| 탭 | 보이는 내용 |
|---|---|
| 기본 (POMP) | 기본 대화의 메시지. 한 번만 보낼 대상을 고르면 그 배지를 표시한다 |
| 에이전트·팀 탭 | 해당 상대와의 독립 대화 기록 및 진행 상태 |

### 에이전트 탭의 맥락

에이전트 탭은 별도 엔진과 기록을 갖고, 역할 지침·모델·도구를 적용한 뒤 메시지를 보낸다.
탭을 오가도 그 역할의 대화 맥락과 진행 중 응답은 이어진다. 메인 대화에서 실행한 하위 에이전트와는
별개의 대화다.

### 팀 탭과 같은 구성원으로 이어 가기

팀 탭의 메시지는 매번 팀으로 간다. 이때 POMP는 이 대화에서 그 팀의 구성원으로 일했던 에이전트를 기억한다.

- 아직 남아 있는 구성원에게는 새로 시작하지 않고 다음 일을 보낸다.
- 목록에 없거나 연결되지 않는 구성원만 새로 시작한다.
- 이어 가는 구성원은 최대 6명이다.
- 남은 구성원이 없으면 "이전 구성원을 찾을 수 없어 새로 시작해요"라고 알리고 새로 시작한다.
- 대화나 연결이 바뀌면 기억을 비운다.
- 격리 팀은 이어 갈 수 없어서 항상 새로 시작한다.

### 메시지 하나만 다른 곳에 보내기

어느 탭에서든 **보낼 대상** 칩, `@` 목록, 메시지가 붙은 `/agent`로 메시지 하나만 다른 상대에게 보낼 수 있다.
그 메시지에만 적용되고, 보낸 뒤 칩은 `보낼 대상`으로 돌아온다.

- 보낸 메시지와 답은 보낸 탭에 남는다. 받은 상대의 탭과 기본 탭에도 보인다.
- 대화를 다시 열거나 엔진·VS를 다시 시작해도 보낸 탭에 그대로 남는다.
- 그래서 한 에이전트의 결과를 다른 에이전트에게 넘겨 작업을 이어 갈 수 있다.

지금 탭의 상대 자신은 칩에 나오지 않는다. 목록에서 그 줄을 고르면 대상이 풀리고 지금 대화로 이어 보낸다.
같은 역할로 실행 중인 구성원은 목록에서 빠진다.

### 늘 POMP로 가는 요청

- `/goal`은 기본 (POMP) 탭에서만 쓴다.
- 계획 이어가기와 편집기의 코드 동작은 메인 POMP로 간다.
- 작업 탭 › 코드 점검의 **에이전트에게 해결 요청**은 지금 보낼 대상에게 메시지 하나로 간다.
  편집기 컨텍스트는 붙지 않고, 항목은 최대 50개, 요청 전체는 12,000자까지다.

## 진행 보기와 구성원 중지

### 작업 카드

채팅의 작업 카드에 구성원별 상태, 도구 수, 시간, 최근 도구가 보인다. 에이전트·팀 대화 상대 탭에도 같은 카드가 나온다.
해당 카드가 없는 구성원은 입력창 위의 접을 수 있는 진행 줄에 나온다.

구성원의 대화는 읽기 전용으로 볼 수 있다. 최근 메시지 40개까지 보이고 긴 글은 잘린다.

### 구성원 하나 멈추기

실행 중인 구성원 줄의 **중지**를 누르고, 같은 줄에서 한 번 더 확인한다.

- 그 구성원만 "취소됨"으로 끝난다. 다른 구성원은 계속 일한다.
- 메인 대화는 취소된 결과를 받아 이어 간다.
- 메인 대화가 응답 중이어도 바로 멈춘다.
- 메인 대화가 직접 시작했거나 다른 구성원을 거쳐 시작한 구성원만 멈출 수 있다.
- 지금 엔진에서 이 기능을 쓸 수 없으면 **중지** 버튼이 나오지 않는다.

채팅 입력창의 중지는 구성원 하나가 아니라 전체 응답을 멈춘다.

### 응답 중에 보낸 메시지 (대기열)

응답 중에 보낸 메시지는 거절하지 않고 대기열에 넣는다. 보낼 대상도 항목과 함께 저장된다.
대기열은 입력창 위에 목록으로 보이고, 이 VS 창이 열려 있는 동안만 남는다.

| 조작 | 동작 |
|---|---|
| 순서 바꾸기 · 고치기 · 지우기 | 항목 하나를 다룬다 |
| 일시정지 · 재개 | 대기열 진행을 멈추거나 다시 시작한다 |
| 비우기 | 모든 항목을 지운다 |

- 응답이 정상으로 끝나면 다음 항목을 보통 메시지처럼 보낸다.
- 오류, 중지, 대화 바뀜이 있으면 대기열을 일시정지하고 이유를 보인다. 항목은 지우지 않는다.
- 대기열은 넣을 때의 대화에 묶인다. 다른 대화에서는 재개를 거부하므로, 그 대화로 돌아가 재개하거나 비운다.

### 실행 기록

팀, 에이전트, 직접 메시지를 실행할 때마다 기록이 남는다. 별도의 기록 관리 화면은 없다.

- 남는 것: 대상, 요청 글 4,000자까지, 시작·끝 시각, 상태, 구성원별 상태·도구 수·토큰·시간
- 남지 않는 것: 프롬프트 전체, 도구 결과, 파일 내용
- 위치: `<작업 영역>\.pomp\local\agent-history.json`

## 승인과 안전

하위 에이전트는 승인 창 없이 자동 승인으로 일한다. 그래서 팀과 에이전트 실행의 권한 경계는 그 실행을 시작하는 `task` 호출의 승인이다.

- 승인 창에 구성원별 할당이 모두 보인다. 승인 전에 누가 무엇을 할지 확인한다.
- `task` 승인은 기억하지 않고 매번 묻는다. "항상 허용"과 "이 세션 동안 허용"이 없다.
- 도구별 정책에서 거부로 둔 도구는 하위 에이전트에게도 거부된다.
- 도구별 정책에서 확인으로 둔 도구는 하위 에이전트가 물을 수 없으므로 거부된다.
- 실행이 바꾼 파일은 체크포인트와 변경 이력에서 보고 되돌릴 수 있다.
- 읽기 도구만 가진 에이전트로 짠 팀은 파일을 바꾸지 않는다.
- 하위 에이전트는 화면·입력 제어와 브라우저 제어를 쓸 수 없다. 팀에서는 리더인 메인 대화만 승인을 받고 쓴다.
- 샌드박스가 아니다. 승인된 명령은 사용자의 원래 권한으로 실행된다.

전체 안전 규칙은 [개요의 안전 모델](overview.md#안전-모델)에 있다.

## 격리된 복사본에서 실행

팀의 **격리된 복사본에서 실행**을 켜면 구성원마다 따로 만든 복사본에서 일한다. 팀 줄에는 **격리** 배지가 붙는다.

- 작업 영역이 Git 저장소여야 한다. 저장하지 않은 변경도 복사본에 들어간다.
- 복사본은 작업 영역의 `.pomp\local\wt` 아래에 만들어진다.
- 구성원의 변경은 파일에 바로 쓰이지 않고 패치로만 남는다.
- 격리된 구성원은 나중에 이어 쓸 수 없어서 격리 팀은 항상 새로 시작한다.
- 권한은 작업 영역의 `.pomp/permissions.json`으로 판단한다. 구성원이 복사본의 정책 파일을 고쳐도 효과가 없다.

### 결과 검토와 적용

구성원이 끝나면 결과가 작업 탭 › 변경 › 대기 중의 **격리 실행 결과**에 들어간다.
줄마다 파일, 종류, 추가·삭제 줄 수, 상태, 이유가 보이고 **적용**, **결과 버리기**, **패치 열기**를 쓸 수 있다.

받을 수 있는 결과는 아래와 같다.

- 텍스트 파일의 추가, 수정, 삭제만 받는다. 이름 바꾸기, 복사, 바이너리 변경은 받지 않는다.
- 패치는 2 MiB까지다.
- 작업 영역 밖의 파일이 하나라도 있으면 그 결과는 **막힘**으로 보인다.
- 바꾼 파일이 없으면 "바꾼 파일 없음" 알림만 남는다.

**적용**은 프로젝트 정책을 확인한 뒤 패치 내용을 담은 승인 창을 연다. 아래 경우에는 적용을 거부한다.

- 저장하지 않은 편집기 변경이 있는 파일
- UTF-8이 아닌 파일
- 있어야 할 파일이 없거나, 새로 만들 파일이 이미 있는 경우
- 패치의 문맥이 지금 파일과 정확히 맞지 않는 경우
- 승인한 뒤 그사이 파일이 바뀐 경우

적용 전 내용은 체크포인트로 남아 변경 이력에서 되돌릴 수 있다. BOM과 줄 끝(CRLF/LF)은 원래대로 둔다.
쓰는 도중 실패하면 이미 쓴 파일을 되돌린다.
적용했거나 실패한 결과는 버릴 때까지 목록에 남는다. **결과 버리기**는 목록에서만 지우고 패치 파일은 남긴다.

## 팀 내보내기와 가져오기

팀과 그 팀이 쓰는 사용자 정의 역할을 글 하나(JSON)로 내보내고, 다른 프로젝트나 PC에서 가져올 수 있다.
엔진 내장 역할은 글에 넣지 않고 이름으로만 가리킨다. 글은 256 KiB까지다.

### 내보내기

팀 줄의 **내보내기**를 누른다. 글을 **복사**하거나 **편집기에서 열기**로 VS에서 열어 원하는 곳에 저장한다.

### 가져오기

1. 팀 카드 머리의 **가져오기**를 누른다.
2. 내보낸 글을 붙여 넣는다.
3. 가져올 범위를 고른다. 이 프로젝트 또는 내 모든 프로젝트다.
4. **미리보기**를 누르고 팀과 역할마다 상태를 확인한다.
5. 가져온다.

| 미리보기 상태 | 뜻 |
|---|---|
| 새로 만듦 | 새 파일로 만든다 |
| 이미 있음 | 같은 내용이 이미 있다 |
| 이름 겹침 | 같은 이름에 다른 내용이 있다. 이 경우 가져올 수 없다 |
| 이 PC에 있음 | 글에는 없지만 이 PC에서 찾은 역할이다 |

가져오기는 새 파일만 만들고 기존 파일을 덮어쓰지 않는다. 하나라도 실패하면 이번에 만든 파일을 지운다.
역할과 팀의 제한은 직접 만들 때와 같다.

## 역할·팀에 지식 붙이기

지식은 도구 탭 › 지식 한 곳에서 관리한다. 역할·팀 편집 창의 **지식**은 그 목록에서 골라 붙인다.

| 붙이는 곳 | 언제 함께 가나 | 한도 |
|---|---|---|
| 역할 | 그 역할이 구성원으로 일할 때마다 | 최신 10개, 역할당 8,000자 |
| 팀 | 그 팀에 메시지를 보낼 때마다. 다른 대상에는 가지 않는다 | 최신 10개, 12,000자 |
| 컨텍스트 바구니 | 체크를 풀 때까지 이 대화의 모든 메시지에 | |

- 고른 지식은 저장할 때 적용된다.
- 지식은 참고 자료로만 전달된다. 도구 권한, 승인, 정책을 바꾸지 않는다.
- 팀에 붙은 지식은 다시 연 대화 화면에서 숨겨진다.
- 에이전트는 지식을 제안만 할 수 있다. 제안은 사용자가 도구 탭 › 지식에서 수락해야 쓰인다.

지식 자체를 만들고 고치는 방법은 [화면 가이드](screen-guide.md)와 [설정 안내](settings.md)에 있다.

## 자동화

에이전트 탭 › 자동화 › **자동화 규칙**에서 이벤트가 났을 때 할 일을 정한다. 실행 결과는 **실행 기록** 카드에서 본다.

### 할 일

| 할 일 | 동작 | 저장 위치 |
|---|---|---|
| 알림 | 채팅에 알림을 띄운다 | `<작업 영역>\.pomp\local\agent-hooks.json` |
| 채팅 | 메인 대화, 에이전트, 팀 중 하나에 보통 채팅 메시지를 보낸다 | `<작업 영역>\.pomp\local\agent-hooks.json` |
| 스크립트 | 파일 저장이나 빌드 때 PowerShell 훅을 실행한다 | `<작업 영역>\.pomp\hooks` |

채팅으로 보내는 메시지는 대기열과 승인을 그대로 거친다. 편집기 컨텍스트는 붙지 않고, 이벤트 요약이 함께 간다.
규칙 개수에는 제한이 없다.

### 이벤트

| 이벤트 | 언제 | 출처 |
|---|---|---|
| 에이전트 끝남 · 에이전트 실패 | 에이전트 실행이 끝나거나 실패했을 때 | 모든 에이전트 또는 역할 이름 |
| 팀 끝남 · 팀 실패 | 팀 실행이 끝나거나 실패했을 때 | 모든 팀 또는 팀 식별자 |
| 피드백 대기 | 케이스 카드가 사용자 의견을 기다릴 때 | |
| 파일 저장됨 | VS에서 파일을 저장했을 때 | 모두 |
| 빌드 성공 · 빌드 실패 | VS 빌드가 끝났을 때 | 모두 |

파일 저장됨은 **저장 경로**로 거를 수 있다. 작업 영역 기준 glob이고 200자까지다. 예: `src/**/*.cs`. 비우면 모든 파일이다.

### 규칙 만들기

1. **+ 새 규칙**을 누른다.
2. **할 일**을 먼저 고른다. 아래 칸이 할 일에 맞게 바뀐다.
3. 이벤트와 출처를 고른다. 파일 저장이면 저장 경로도 적는다.
4. 채팅이면 대상과 **보낼 메시지**를 적는다.
5. 이름을 적고 **사용** 스위치를 켠 뒤 저장한다.
6. 카드 머리의 **이 대화에서 사용**을 켠다.

### 안전장치

- 채팅 전달은 **이 대화에서 사용**이 켜져 있을 때만 한다. 같은 스위치가 훅이 이벤트를 듣는 것도 켜고 끈다.
- 이 스위치는 대화마다 따로이고, 대화가 바뀌거나 다시 연결되면 꺼진다.
- 전달은 대화당 10번까지다. 한도에 닿으면 카드 머리에 **전달 한도 도달** 배지가 붙는다.
- 같은 이벤트는 한 번만 처리한다.
- 규칙이 보낸 메시지로 생긴 이벤트는 다시 전달하지 않는다. 연쇄는 한 단계까지다.
- 팀 결과를 같은 팀에 되보내는 규칙은 만들 수 없다.
- 다시 연결한 뒤 처음 본 작업이 이미 끝나 있었으면 이벤트를 내지 않는다.
- 실패한 응답 뒤 멈춘 대기열은 규칙이 다시 움직이지 않는다. 사용자가 재개해야 한다.

파일 저장과 빌드 이벤트에는 아래가 더해진다.

- 대화가 쉬는 중일 때만 처리한다. 에이전트가 고친 파일을 저장해서 규칙이 다시 도는 일을 막는다.
- 규칙마다 60초가 지나야 다시 보낸다.
- 그 규칙이 보낸 메시지가 아직 대기열에 있거나 실행 중이면 이번 이벤트는 건너뛴다.
- 이벤트 요약에는 작업 영역 기준 경로나 빌드 결과만 담는다. 파일 내용은 보내지 않는다.

스크립트 훅을 만드는 칸은 [화면 가이드](screen-guide.md)에 있다.

## 컴퓨터 사용

컴퓨터 사용은 에이전트가 화면을 보고 클릭·입력하게 하는 기능이다. 대화마다 따로 켜고, 처음에는 꺼져 있다.

| 설정 | 위치 | 기본 |
|---|---|---|
| 컴퓨터 사용: 사용 안 함 / 대화마다 켜기 | 도구 > 옵션 > Pomp > 일반 > 컴퓨터 사용 | 대화마다 켜기 |
| 브라우저 제어 | 같은 곳. 다시 시작해야 적용된다 | 끔 |
| 화면 보기도 매번 확인 | 같은 곳 | 끔 |
| 이 대화에서 화면 입력 제어 | 채팅 입력창의 화면 입력 제어 버튼(Live 오른쪽) | 꺼짐 |

- 입력창에서 `/computer`를 치면 같은 버튼을 누른 것과 같다.
- 옵션이 사용 안 함이면 버튼이 숨겨지고 `/computer`도 거부된다.
- 켤 때 "이 대화에서 화면 입력 제어를 켤까요?"로 확인을 받는다. 켜져 있으면 버튼이 눌린 모양이 된다.
- 응답 중에는 켤 수 없고 끌 수만 있다.
- 한 PC에서 한 대화만 쓴다. 다른 대화 상대 탭이나 다른 Visual Studio의 POMP가 쓰는 동안 이 버튼은 꺼진 채 눌리지 않고, 툴팁에 "다른 대화에서 사용 중: 이름"이 나온다.
- 켠 탭에서 다른 탭으로 가면 그동안 화면 입력 제어가 꺼지고, 그 탭으로 돌아오면 다시 켜진다. 메시지가 없던 대화여도 같다(돌아오면 그 탭의 새 대화에서 켜진다).
- 쓰던 대화가 끄거나, 그 탭을 닫거나, 그 탭에서 새 대화를 시작하거나, 엔진이 다시 시작되거나, Visual Studio를 닫으면 다른 대화에서 다시 누를 수 있다.
- 권한 모드가 `모두 자동`이면 화면 동작을 묻지 않는다.
- 다른 모드에서는 화면을 다루는 Eval 호출을 실행 전에 묻는다.
- 화면 동작 하나하나(클릭·입력·클립보드 쓰기, 화면 보기도 매번 확인이면 화면 보기까지)를 따로 묻는 것은 고급 옵션 **에이전트 질문을 채팅에 표시**가 켜져 있을 때만 된다. 자세한 표는 [설정 안내](settings.md#안전)에 있다.
- 하위 에이전트는 화면·브라우저 제어를 쓸 수 없다.
- 화면에 보이는 정보는 믿을 수 없는 입력으로 다룬다.

옵션의 자세한 설명은 [설정 안내](settings.md)에 있다.
